## 1. 두 모델을 고른 이유

목표는 두 가지다. **(1) 포즈가 오류 없이 추정되는가**, **(2) 사람별 ID를 놓치지 않는가**. 이 중 (2)는 VTG 질의(`a woman in a red jacket opens the refrigerator`)에서 *어느 사람*인지 지정하려면 필수다.

선정 기준은 "최신"이 아니라 **ID 유지 전략이 정반대인 두 모델**이었다. 한쪽이 무너지는 지점에서 다른 쪽이 어떻게 하는지를 봐야 답이 나오기 때문이다.

| 모델 | ID 유지 전략 | 바디 모델 | 발표 |
| --- | --- | --- | --- |
| CoMotion | 이전 포즈를 새 프레임으로 **직접 갱신** (순환 상태). 외모 기억 없음 | SMPL | ICLR 2025 · Apple |
| Multi-HMR 2 | 프레임별 검출 후 **SAM2 외모 특징으로 연결** (기억으로 재식별) | Anny | 2026.06 · NAVER LABS Europe |

### 기각한 대안

- **4D-Humans** (2023) — CoMotion이 이미 명확히 앞서 결과가 자명함
- **WHAM / TRAM / GVHMR** (월드좌표 계열) — 우리 카메라는 COLMAP으로 캘리브레이션된 고정 리그다. "카메라를 모를 때" 푸는 문제를 비싸게 푸는 셈
- **PromptHMR** — SMPL-X·정확도는 우수하나 DROID-SLAM 등 설치 부담이 인스턴스 재구축마다 반복됨
- **Multi-THuMBS** (2026) — 코드 미공개
- **SMPLest-X / AiOS** — 트래킹 기능 없음

## 2. CoMotion 상세

> **CoMotion: Concurrent Multi-person 3D Motion**
> Newell, Hu, Lipson, Richter, Koltun · ICLR 2025
> arXiv:2504.12186 · github.com/apple/ml-comotion

### 2.1 핵심 아이디어

기존 트래커는 **탐지 후 매칭**이다. 프레임마다 사람을 찾고 이전 프레임과 짝짓는다. 가려져서 탐지가 안 되면 짝지을 대상이 없어 트랙이 끊긴다.

CoMotion은 **탐지 결과를 갱신**한다. 트랙의 상태(포즈 + GRU 은닉상태)를 들고 있다가, 새 이미지를 보고 "이 사람의 포즈를 어떻게 바꿔야 하나"를 직접 예측한다.

### 2.2 아키텍처

```
이미지 인코더 — ConvNeXtV2
  멀티해상도 피라미드 1/8 · 1/16 · 1/32
  1/8 해상도로 선형투영 후 합산 융합
  회전 위치 임베딩(RoPE): 픽셀 좌표 + 월드 좌표
        |
   +----+-----+
   |          |
 탐지 단계     포즈 갱신 단계
 단발 검출기    사람당 토큰 24개 x 512차원
 격자 위치당    (이전 SMPL 파라미터 + 2D 투영 키포인트
 포즈 4개        + 은닉상태를 토큰으로 인코딩)
 512x512당      이미지 특징에 cross-attention
 ~1,344 후보    GRU 로 은닉상태 갱신
 -> NMS         사람간 · 사람내 트랜스포머 레이어
 1x1 conv 로
 SMPL(감마,세타,베타)
 + 신뢰도 출력
```

### 2.3 학습 데이터와 커리큘럼

| 단계 | 반복 | 자원 | 데이터 | 학습 대상 |
| --- | --- | --- | --- | --- |
| 1 · 단일 이미지 | 400K | 32 x A100 / 3일 | InstaVariety · COCO · MPII (NLF 의사라벨), BEDLAM (합성 GT) | 인코더 + 탐지 모듈 |
| 2 · 8프레임 클립 | 200K | 3일 | BEDLAM · WHAC-A-MOLE, PoseTrack · DanceTrack (의사라벨) | 포즈 갱신 모듈만 (인코더·탐지 동결) |
| 3 · 장기 시퀀스 | 50K | 1.5일 | DanceTrack 96프레임, WHAC-A-MOLE 32프레임 | 포즈 갱신 모듈 미세조정 |

손실은 L1 2D 재투영 오차, L1 루트정규화 3D 관절 오차, L2 SMPL 각도 차이다.

**실제 영상의 3D 정답은 존재하지 않으므로** NLF로 의사라벨을 만들어 쓴다. 이것이 클로즈업에서 성능이 떨어지는 원인으로 논문에 명시돼 있다.

### 2.5 트랙 생성·소멸 규칙 (코드 실측)

```
init_conf_thr      = 0.2    신뢰도 0.2 넘는 검출이 새 트랙 후보
init_match_thr     = 0.75   기존 트랙과의 매칭 임계
missing_match_thr  = 0.2    기존 트랙과 안 맞으면 새 트랙 생성
overlap_thr        = 0.6    두 트랙이 0.6 이상 겹치면 "붕괴 후보"
overlap_time_thr   = 20     20프레임 이상 겹치면 하나를 삭제
vel_outlier_thr    = 0.25   속도 이상치 판정
max_output_tracks  = 48     트랙 상한
```

추가로 `ContentDetector(threshold=50.0, min_scene_len=3)` 가 장면 전환을 감지해 `shot_reset` 으로 **모든 트랙을 지운다**.

### 2.6 논문이 밝힌 한계

- **긴 가림을 뚫지 못하고 재식별(re-identification)을 하지 못한다** — 외모를 저장하지 않는 구조라 상태가 끊기면 그 사람을 다시 알아볼 수단이 없다
- 포즈가 똑같아지면 트랙이 하나로 붕괴한다
- 가끔 트랙이 갑자기 다른 사람으로 옮겨간다
- 물리 개념이 없어 발이 땅에 붙지 않는다
- NLF 의사라벨 품질 문제로 클로즈업·잘린 인물에서 성능 저하
- 고정 길이 클립으로 학습하고 무한 길이로 추론하는 train-test 불일치
- 카메라 움직임을 모델링하지 않고, 절대 스케일도 다루지 않음
- SMPL이 아동 체형을 표현하지 못함

### 2.7 실제 동작

> **[ 영상 넣는 칸 ]**
> 파일: `vis/comotion_Data1.mp4` (농구 300프레임)
> 볼 것: 코트 위 선수들에 골격이 붙어 따라가는 모습. 좌상단에 프레임 번호와 그 프레임의 트랙 수가 표시된다. 박스 위 숫자가 트랙 ID이며, 같은 사람에게 같은 숫자가 유지되는지가 핵심이다.

## 3. Multi-HMR 2 상세

> **Multi-HMR 2: Multi-Person Camera-Centric Human Detection, Mesh Recovery and Tracking**
> NAVER LABS Europe · 2026.06
> arXiv:2606.14841 · github.com/naver/multi-hmr2

### 3.1 핵심 아이디어

DETR로 사람을 객체처럼 검출하면서 **장면 일관 카메라를 함께 예측**한다. 기존 방식은 초점거리를 모르니 "크게 보이는 게 가까워서인가 원래 큰 사람이라서인가"를 구분하지 못한다. 카메라를 같이 추정하면 실제 미터 단위 3D 위치가 나온다.

추적은 **비디오 학습 없이** 얻는다. SAM2의 메모리 특징을 정지 이미지 단계에서 증류해 두고, 추론 시 그 특징으로 프레임 간 ID를 연결한다.

### 3.2 아키텍처

```
ViT-Large 인코더 (DINOv3 초기화)
  입력 긴 변 768px, 학습 시 무작위 종횡비 크롭
        |
   +----+------+
   |           |
 cls 토큰      학습된 human query 100개
  | MLP          | 디코더 블록 8개
카메라 내부      (self-attn · cross-attn · MLP)
파라미터            |
= 수직 FOV       사람당 출력 헤드
(fx=fy 가정,      - 검출 점수
 주점 중앙)       - 2D 픽셀 위치
                  - 깊이 (log 공간)
                  - Anny 파라미터 (6D 회전)
                  - 트래킹 특징
```

### 3.3 SAM2 증류 — 비디오 없이 추적을 배우는 방법

```
[학습 · 오프라인]
  GT 세그멘테이션 + 이미지
        | SAM2 (Hiera-L) 이미지 인코더
        | SAM2 메모리 인코더
     64 x 64 x 64 표현
        | 8x8 평균풀링 + 평탄화
     4096차원 벡터   <- 이것을 흉내내도록 학습

[추론 · 프레임 간 연결]
  1) 트래킹 특징끼리 KNN (K=35, L1 거리)
  2) + 골반 궤적 기반 운동 예측
     (과거 8개 포즈에 릿지 회귀)
```

### 3.4 학습 데이터

| 구분 | 데이터셋 | 라벨 |
| --- | --- | --- |
| 합성 | Anny-One · BEDLAM | 완전한 3D GT |
| 실제 · 메쉬 | MS-COCO · MPII · AIC | CameraHMR 의사 GT 메쉬 |
| 실제 · 2D만 | MS-COCO · OpenImages | ViTPose 의사 2D 라벨 |

학습 자원은 **단일 GPU로 약 1주**다. CoMotion의 32 x A100 / 7.5일과 대비된다. 효율적인 2D 기반 매칭 전략 덕분이라고 논문은 설명한다 (forward-backward 0.35초 / 메모리 7GB, 전체 바디모델 매칭은 0.48초 / 27GB).

### 3.5 바디 모델 — Anny

논문은 **163개 뼈 방향**과 **해석 가능한 체형 파라미터 6개**로 설명한다. 채택 이유는 명시적이다. 기존 파라메트릭 모델은 성인 몸만 표현할 수 있어 **아이가 있으면 3D 위치 오차가 커진다**.

> **문서와 실측의 차이**
> 실제 출력의 `shape` 텐서는 **(N, 11)** 이었다. 논문의 "6개"와 다르다. 우리 파이프라인은 이 11개를 `betas_native` 에 원본 그대로 보존하므로 해석이 확정되지 않아도 정보 손실은 없다.

### 3.6 보고된 성능

| 데이터 | 지표 | Multi-HMR 2.b | AiOS | SAT-HMR | Multi-HMR v1 |
| --- | --- | --- | --- | --- | --- |
| 3DPW | PA-MPJPE | **41.8** | 45.0 | 52.7 | 46.9 |
| 3DPW | PVE | **78.1** | 90.9 | 94.5 | 88.8 |
| 3DPW | TA-PVE | **161.9** | 774.3 | 174.5 | 187.2 |
| EMDB | Abs-PVE | 374.8 | 11,962.1 | 1,093.0 | **168.1** |
| MSCOCO | AP | **50.7** | 44.9 | 42.1 | 31.2 |
| PoseTrack21 | IDF1 | 75.2 | — | — | — |

주목할 점 둘.

- **MSCOCO AP가 v1의 31.2에서 50.7로** 크게 올라 검출이 압도적으로 개선됐다
- 반대로 **EMDB 절대 위치 정확도는 v1보다 나빠졌다** (374.8 vs 168.1). 논문이 숨기지 않고 표에 냈다

### 3.7 논문이 밝힌 한계

- 카메라 모델이 fx=fy, 주점 중앙을 가정하고 **렌즈 왜곡을 모델링하지 않는다**
- 2D·3D 지도학습을 섞으면 포즈 사전분포가 왜곡돼 **가림 시 앉은 자세를 자주 예측한다**
- DETR 계열이라 학습 수렴이 느리다
- 추적이 SAM2 증류 품질에 의존하며 운동 기반 방식과 독립 비교되지 않았다

> **[ 영상 넣는 칸 ]**
> 파일: `vis/multihmr2_Data1.mp4` (농구 300프레임, 중복 제거 전)

## 4. 구조 대조

| 항목 | CoMotion | Multi-HMR 2 |
| --- | --- | --- |
| 백본 | ConvNeXtV2 멀티스케일 피라미드 | ViT-Large (DINOv3 초기화), 768px |
| 검출 | 단발 검출기, 512x512당 후보 ~1,344 → NMS | DETR, 학습된 query 100개 → 3D 골반 NMS |
| 시간 연결 | GRU 순환 상태 (사람당 토큰 24 x 512) | SAM2 특징 KNN(K=35) + 골반 릿지회귀 |
| 비디오 학습 | 필요 (8 → 96프레임 커리큘럼) | 불필요 (정지 이미지 + 증류) |
| 학습 자원 | 32 x A100 / 약 7.5일 | 단일 GPU / 약 1주 |
| 카메라 | 약원근 근사 K=[[2·max(W,H),0,W/2],...] | 장면 일관 내부 파라미터 예측 |
| 바디 모델 | SMPL — 베타 10, 세타 72 | Anny — 163본, 체형 11개(실측) |
| 체형 파라미터 | **트랙마다 고정** (실측 변동 0) | 프레임마다 재추정 |
| 재식별 | **없음** — 외모를 저장하지 않음 | **있음** — SAM2 특징 4096차원 |
| 주된 실패 양상 | **단편화** — 트랙이 끊겨 이어달리기. ID 숫자가 바뀌어 *보인다* | **정체 혼동** — 트랙은 살아있는데 사람이 바뀜. *안 보인다* |

> **더 위험한 쪽**
> 정체 혼동이 단편화보다 위험하다. 단편화는 ID 숫자가 바뀌므로 눈에 띄고 후처리로 이어붙일 수 있다. 정체 혼동은 ID가 그대로라 알아채지 못한 채 지나간다. VTG에서 "빨간 자켓 여자"를 지정했는데 중간에 조용히 다른 사람으로 바뀌면 결과가 틀린 줄도 모른다.

### 4.1 두 모델 나란히 보기

> **[ 영상 넣는 칸 ]**
> 파일: `vis/compare_Data4.mp4` (golden 660프레임, 왼쪽 CoMotion / 오른쪽 Multi-HMR 2)
> 볼 것: **오른쪽 Multi-HMR 2의 트랙 1번과 2번을 주목한다.** ID 숫자는 바뀌지 않는데 가리키는 사람이 중간에 서로 뒤바뀐다. 왼쪽 CoMotion은 반대로 ID 숫자가 자주 바뀌지만 각 조각이 올바른 사람을 가리킨다. 위 표의 "단편화 vs 정체 혼동"이 눈으로 보이는 지점이다.

## 5. 코드를 가져온 방식

결론부터. **두 모델의 추론·추적 파라미터는 하나도 바꾸지 않았다.** 공식 저장소를 그대로 clone해 기본값으로 실행하고, 출력을 읽어 공통 포맷으로 옮기기만 했다.

### 5.1 추론 호출 — 전문

| 모델 | 호출 | 넘긴 인자 |
| --- | --- | --- |
| CoMotion | `demo.py` 를 서브프로세스로 실행 | `-i` 입력, `-o` 출력, `--skip-visualization`, `--num-frames`(파일럿 한정). **모델 파라미터 인자 없음** |
| Multi-HMR 2 | `api.infer_video(session, path, tmp)` | 전부 기본값 (`conf_thresh=0.4`, `dist_thresh_nms=0.25`). **인자를 넘기지 않음** |

> **CLI 대신 Python API를 쓴 이유**
> Multi-HMR 2의 `multihmr2 --save_anny_params` 는 K·shape·pose_parameters만 저장하고 **트랙 ID를 남기지 않는다**. ID 유지가 평가의 축이므로 쓸 수 없었다. `api.infer_video()` 는 내부에서 `FeatPelvisTracker` 를 돌려 `track_id` 를 채운 `DecoderOutput` 을 프레임별로 돌려준다. **추적 로직 자체는 모델 것 그대로다.**

### 5.2 환경 문제로 조정한 것 (모델 파라미터 아님)

| 문제 | 원인 | 조치 |
| --- | --- | --- |
| `chumpy` 빌드 실패 | `setup.py` 가 pip를 임포트하는데 pip의 빌드 격리 환경에는 pip가 없다 | `--no-build-isolation` 으로 선설치 |
| `scenedetect` API 불일치 | CoMotion이 버전을 고정하지 않아 최신 0.7.1이 설치됨. `process_frame` 이 int 대신 timecode 객체를 요구 | `scenedetect<0.7` 고정 (0.6.7.1) |
| `.[all]` 불필요 의존성 | `aitviewer`(3D 뷰어)가 헤드리스 MIG 환경에 불필요 | 기본 의존성만 설치 |
| 메쉬 렌더링 불가 | MIG 인스턴스는 OpenGL/Vulkan을 지원하지 않음 (NVIDIA 공식 문서) | `--render` 제거. 시각 검증은 자체 PIL 오버레이로 |

### 5.3 우리가 작성한 부분

```
모델 출력  ->  [ 우리 코드 ]  ->  tracks.npz  ->  [ 지표 코드 한 벌 ]

CoMotion .pt      id / pose(72) / trans / betas / frame_idx
   -> 관절 3D: CoMotion 내장 SMPLKinematics 로 순전파
   -> 2D:      get_default_K 와 동일한 근사 내부파라미터로 투영
   -> bbox:    joints2d 에서 유도

Multi-HMR 2 DecoderOutput   track_id / conf / shape / v3d / j3d / j2d
   -> 관절:    anny 내장 COCO 회귀기로 정점 19,158개에서 COCO-17+발6 추출
   -> 2D:      모델이 예측한 K 로 투영 (모델 j2d 와 0.07px 일치 확인)
   -> bbox:    joints2d 에서 유도
```

> **Anny → SMPL 변환이 불필요해진 경위**
> 설계 단계에서 "최대 리스크"로 지목했던 단계다. 그런데 `anny` 패키지가 COCO 키포인트 회귀기를 내장하고 있어(`data/keypoints/coco.pth`, 가중치 23 x 19,158) 메쉬 정점에서 COCO-17을 직접 뽑을 수 있고, **우리 GT가 바로 그 COCO-17** 이었다. 리토폴로지·피팅 없이 직결된다.
> 검증 — 허벅지 0.366m, 정강이 0.352m, 상완 0.243m, 전완 0.206m, 허벅지/상완 1.51 (실제 인체 약 1.5)

## 7. 중복 스켈레톤 문제

Multi-HMR 2 결과에서 **한 사람에게 두 개의 스켈레톤이 씌워지는** 현상이 관찰됐다. 원인 규명과 해결 과정이다.

### 7.1 원인 — 3D 공간 NMS x 단안 깊이 모호성

Multi-HMR 2의 중복 제거는 **3D 골반 거리** 기준이다 (`dist_thresh_nms = 0.25 m`). 단안 추정에서 깊이는 본질적으로 부정확하므로, 화면상 같은 위치의 두 검출이 **깊이만 크게 벌어져** 3D 거리 임계값을 통과한다.

| 농구 · 2D 겹침 > 0.3 인 검출 쌍 1,030개 | 중앙값 |
| --- | --- |
| 2D IoU | 0.548 |
| 3D 골반 거리 | 2.002 m |
| 그중 수평(xy) 성분 | 0.187 m |
| 그중 **깊이(z) 성분** | **1.996 m** |
| NMS 임계값 0.25m 통과 비율 | **100 %** |
| 깊이 차 > 수평 차인 비율 | 99 % |

**거리의 전부가 깊이다.** 화면에서는 같은 사람인데 예측 깊이만 2m 벌어져 둘 다 살아남는다.

> **왜 임계값을 키우면 안 되는가**
> `dist_thresh_nms` 를 2m로 올리면 **실제로 2m 떨어져 서 있는 다른 사람**까지 지워진다. 판정을 3D가 아닌 **화면 공간**에서 해야 한다.

### 7.2 1차 시도와 그것이 부족했던 이유

화면 공간에서 IoU 기준으로 중복을 지웠다. 테니스에서 크게 개선됐지만 일부가 남았다. 남은 사례를 직접 재보니:

| 테니스 프레임 1097 · 검출 id45 ↔ id51 (같은 선수) | 값 | 판정 |
| --- | --- | --- |
| 2D IoU | 0.385 | 임계값 0.55 미만 → 통과해버림 |
| IoS (작은 박스 대비 겹침) | 0.771 | 명확한 중복 |
| 면적비 | 0.56 | 한쪽이 절반 크기 |
| 깊이 차 | 5.84 m | 투영 크기가 달라진 원인 |

**깊이 오차는 투영 *크기* 도 바꾼다.** 같은 사람이 5.8m 다른 깊이로 잡히면 한쪽 박스가 절반 크기가 되고, IoU는 교집합/합집합이라 크기가 다르면 값이 급락한다.

### 7.3 해결 — IoU 또는 (IoS + 동심)

```
중복으로 판정하는 조건 (둘 중 하나)

  조건 A.  2D IoU >= 0.55                        크기가 비슷한 중복

  조건 B.  IoS >= 0.70  그리고  중심 offset < 0.25   크기가 다른 동심 중복
           IoS    = 교집합 / 작은 쪽 면적
           offset = 두 중심 거리 / 작은 쪽 대각선
```

> **동심 조건이 안전장치인 이유**
> IoS만 쓰면 **가까운 사람 뒤에 서 있는 진짜 다른 사람**도 지워진다. 같은 사람의 중복은 두 박스가 동심이고, 뒤에 선 사람은 큰 박스 안 한쪽에 치우친다. 회귀 테스트로 이 구분을 고정해 뒀다 — IoU만으로는 놓치는 것, IoS로 잡는 것, 동심이 아닌 포함관계는 보존하는 것.

### 7.4 효과 (GT로 검증)

purity가 떨어지면 진짜 사람을 지운 것이다. 떨어지지 않았다.

| 영상 | purity 전 | purity 후 | 최저 전 | 최저 후 | 트랙 수 |
| --- | --- | --- | --- | --- | --- |
| 테니스 | 0.937 | **0.997** | 0.883 | **0.994** | 81 → 53 |
| 농구 | 0.609 | 0.615 | 0.337 | 0.353 | 64 → 58 |
| golden | 0.720 | 0.719 | 0.568 | 0.567 | 8 → 7 |
| OnlyOneOf | 1.000 | 1.000 | 1.000 | 1.000 | 2 → 2 |

### 7.5 전후 비교 영상

> **[ 영상 넣는 칸 — 이 문서에서 가장 중요한 영상 ]**
> 파일: `vis/nms_effect_Data2.mp4` (테니스, 왼쪽 원본 / 오른쪽 중복 제거)
> 볼 것: **프레임 1097 부근**. 왼쪽에서 코트 아래쪽 선수 한 명에게 박스가 두 개(id 45, id 51) 겹쳐 있다가, 오른쪽에서는 하나만 남는다. 위 표의 IoU 0.385 / IoS 0.771 사례가 바로 이것이다.

> **[ 영상 넣는 칸 (선택) ]**

> 볼 것: 개선이 테니스만큼 크지 않다는 것. 아래 "한계" 항목의 근거다.

### 7.6 한계

> **만능이 아니다**

## 8. 추적 실패의 진짜 원인

ID가 바뀌는 순간마다 주변 상황을 기록해 원인을 좁혔다. 가설은 넷이었다 — 가림 / 화면 경계 / 이동 속도 / 인물 크기.

**Data1 농구 · CoMotion · ID 변경 26회 vs 유지 3,607프레임**

| 조건 | 변경 순간 | 유지 중 | 차이 |
| --- | --- | --- | --- |
| **가림 (IoU)** | 0.193 | 0.046 | **4.2배** |
| 경계 거리 | 0.308 | 0.256 | 1.2배 |
| 화면내 키 | 0.210 | 0.206 | 1.0배 |
| 이동 속도 | 0.137 | 0.084 | 1.6배 |

**Data4 golden · CoMotion · ID 변경 13회**

| 조건 | 변경 순간 | 유지 중 | 차이 |
| --- | --- | --- | --- |
| **가림 (IoU)** | 0.246 | 0.000 | 무한대 |
| 경계 거리 | 0.384 | 0.398 | 0.96배 |

| 관찰 | 값 |
| --- | --- |
| 농구 · ID 변경 순간이 가림 IoU>0.2 | **46 %** (유지 중에는 16%) |
| golden · 같은 조건 | **62 %** (유지 중에는 6%) |
| 화면 경계에서 바뀐 경우 | **0 %** — 경계는 원인이 아님 |

**가림이 압도적인 원인이다.** 경계·크기·속도는 거의 무관하다.

이는 모델 구조와 정확히 맞물린다. 두 사람이 겹치면 두 트랙이 같은 위치를 가리키고, `overlap_thr=0.6` / `overlap_time_thr=20` 규칙이 하나를 중복으로 판정해 삭제한다. 겹침이 풀리면 사라진 사람에게 새 트랙이 부여된다.

> **확인하고 배제한 것**
> CoMotion의 장면 전환 리셋은 무죄다. `ContentDetector` 를 우리 4개 영상에 직접 돌린 결과 **컷 검출 0회** 였다. 전부 단일 샷이다. 추적 로직은 전적으로 모델 것이며 우리 코드는 출력을 읽고 정규화만 한다.

### 8.1 가림 순간 확인

> **[ 영상 넣는 칸 ]**
> 파일: `vis/comotion_Data4.mp4` (golden 660프레임)
> 볼 것: 세 번째 댄서의 ID가 `4 → 6 → 19 → 26` 으로 넘어가는 지점. 다른 댄서와 겹치는 순간에 바뀐다. 위 표의 "변경 순간 가림 IoU 0.246 vs 유지 중 0.000" 이 눈으로 보이는 지점이다.

> **단안의 근본 한계**
> CoMotion 논문이 직접 밝힌 한계와 일치한다 — "긴 가림을 뚫지 못하고 재식별을 하지 못한다". 외모를 저장하지 않는 구조라 상태가 끊기면 그 사람을 다시 알아볼 수단이 없다. Multi-HMR 2는 반대로 SAM2 외모 특징을 쓰지만, 그래서 비슷하게 생긴 사람끼리 헷갈려 정체가 뒤바뀐다.
> **가려진 사람을 한 대의 카메라로 계속 따라가는 것은 정보가 없어 불가능하다.** 우리 데이터셋은 같은 장면을 4대가 동시에 찍으므로, 멀티뷰 융합이 이 문제의 구조적 해답이다.

## 9. 평가 코드에서 고친 것

모델이 아니라 **우리 측정 도구**의 결함이다. 셋 다 결론을 뒤집을 수 있는 규모였으므로 함께 기록한다.

### 9.1 bbox 생성 방식 불일치 (치명적)

Data3에서 CoMotion이 트랙 2개를 완벽 유지(스왑 0, 인원수 MAE 0.00)했는데 IDF1이 **0.078** 로 나왔다.

| | bbox 출처 | 크기 | GT와의 IoU |
| --- | --- | --- | --- |
| GT | 투영된 관절에서 유도 | 198 x 547 | — |
| Multi-HMR 2 | 투영된 관절에서 유도 | 208 x 597 | **0.843** |
| CoMotion | 모델의 MOT 검출 박스 | 300 x 749 | **0.482** |

CoMotion의 MOT bbox는 여백을 준 검출 박스라 각 변이 1.28~1.68배 크다. IoU가 임계값 0.5 **바로 아래** 에 걸려 매칭이 전부 실패했다. 추적 품질이 아니라 **bbox 관례 차이** 로 점수가 갈린 것이다.

수정 후 IDF1: Data3 0.078 → **1.000**, Data4 0.237 → **0.795**, Data1 0.543 → **0.666**

### 9.2 지터를 3D 전체로 측정

CoMotion Data4에서 전체 가속 628 중 z 성분이 618 (**98%**) 이었다. 댄서의 루트 z가 34.6~41.4m로 요동하는데 제자리 춤이라 물리적으로 불가능하다. 단안 깊이 추정의 본질적 불안정성이다.

3D 전체로 재면 모델 비교가 **깊이 추정 품질 비교** 로 변질된다. → xy(화면평면)와 z(깊이)를 분리하고, **GT를 기준선으로** 배율을 낸다. 춤은 원래 가속이 크므로 기준선 없이는 해석할 수 없다.

### 9.3 GT 불완전성이 IDF1을 오염

테니스 GT는 선수 2명만 표시하는데 화면에는 볼키즈·심판·관중 등 9~10명이 있다. IDF1은 GT에 없는 사람을 검출하면 오검출로 처벌하므로 **모델이 올바르게 더 많이 찾을수록 점수가 낮아진다**.

실측 — CoMotion이 GT 2명을 **2,308/2,308 프레임 완벽 추적** 했는데 IDF1은 0.347이었다. 낮은 점수의 원인은 정체 실패가 아니라 GT 불완전성이다.

> **대안 지표 — gt_track_purity**
> GT 트랙마다 "가장 많이 대응된 예측 트랙이 전체 프레임의 몇 %를 차지하는가"를 잰다. GT에 없는 검출에 영향받지 않는다. 회귀 테스트로 대조 확인했다 — GT 밖 사람을 추가 검출하면 purity는 유지되고(>0.99) IDF1은 떨어진다(<0.9).

## 11. VLA 적용 관점 — 무엇이 남아 있는가

최종 목표는 복원한 메쉬/3D를 VLA(로봇 정책)에 입히는 것이다. 그 관점에서 두 모델의 출력이 각각 무엇을 제공하는지 점검했다.

### 11.1 메쉬 복원 가능 여부 (저장된 tracks.npz 기준, 실측)

| 필드 | CoMotion | Multi-HMR 2 |
| --- | --- | --- |
| `betas` (체형 10) | 유한값 100% | **NaN 100%** |
| `global_orient` (루트 회전 3) | 유한값 100% | **NaN 100%** |
| `body_pose` (관절 회전 23x3) | 유한값 100% | **NaN 100%** |
| `transl` (루트 위치 3) | 유한값 100% | 유한값 100% |
| `joints3d` (24관절) | 유한값 100% | 유한값 58.3% (COCO 매핑분만) |
| `betas_native` (Anny 체형 11) | 없음 | 유한값 100% |
| **메쉬 복원** | **가능 — SMPL 순전파로 6,890 정점** | **불가 — 자세 파라미터 미보존** |

Multi-HMR 2의 자세는 163본 x 4x4 변환행렬(`bone_poses`)로 표현되는데, 평가에는 관절 위치만 필요해 보존하지 않았다. 사람·프레임당 약 10KB라 전수 보존 시 2GB를 넘는다. 메쉬가 필요해지면 **해당 구간만 재실행**하는 편이 낫다.

### 11.2 SMPL 계열 사용 여부

| 모델 | 바디 모델 | SMPL 계열인가 |
| --- | --- | --- |
| CoMotion | **SMPL** | 그렇다. 베타 10개 + 세타 72개를 그대로 출력 |
| Multi-HMR 2 | Anny | 파라메트릭 인체 모델이지만 **SMPL 계보는 아니다**. MakeHuman 자산과 인체계측 지식 기반의 별개 계열 |

### 11.3 VLA 목적에서의 함의

추적 지표와 별개로, **로봇에 입히는 목적에서도 CoMotion의 SMPL 출력이 유리하다.**

| 항목 | SMPL (CoMotion) | Anny (Multi-HMR 2) |
| --- | --- | --- |
| 메쉬 생성 | 표준 SMPL 순전파 | Anny 라이브러리 필요 |
| AMASS 모션 사전 | SMPL 기반이라 바로 호환 | 변환 필요 |
| 휴머노이드 리타게팅 | SMPL 경유가 사실상 표준 경로 | 확립된 경로 없음 |
| 물리 시뮬 연동 | SMPL 기반 도구가 다수 | 도구 부족 |
| 라이선스 | 등록 후 비상업 연구용 | Apache 2.0 (smplx 토폴로지만 비상업) |

### 11.4 남은 작업

- 멀티뷰 융합 — 가림으로 인한 ID 손실의 구조적 해답 (8장 참조)
- 메쉬 내보내기 경로 — tracks.npz 에서 SMPL 메쉬(6,890 정점) 또는 BVH 로 변환
- 손·얼굴 확장 여부 — 현재 GT(COCO-17)에는 손가락 정답이 없어 **정확도 검증이 불가능하다**. VLA 에서 손 동작이 필요하면 SMPL-X 급 모델을 별도로 도입해야 하며, 그 정확도는 다른 방법으로 검증해야 한다
